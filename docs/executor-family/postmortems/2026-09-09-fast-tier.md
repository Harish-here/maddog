# Postmortem — `executor-fast` and `executor-fast-read`

## Summary

Both agent contracts have a strong core design: they enforce narrow scope, reject ambiguity instead of guessing, separate mechanical execution from judgment, and require faithful reporting.

The main weaknesses are not architectural. They are **contract-boundary issues** that can cause either unnecessary blocking or inconsistent behavior.

---

## 1. `executor-fast`

### What is working well

- Clear separation from `executor-fast-read`, `executor-smart`, and `researcher`.
- Strong “do not guess” / Andon Cord behavior.
- Good scope control through Chesterton's Fence + YAGNI.
- Explicit protection against destructive one-way operations.
- Recovery requires volatile evidence to be captured before remediation.
- GATE prevents changing tests or acceptance criteria to manufacture success.
- REPRODUCE correctly requires evidence before explaining a bug.
- TRANSFORM explicitly requires total coverage and reporting of misfits.
- `NOT DONE` makes partial execution visible.
- Secret redaction is explicitly required.

### Findings

#### P0 — Missing default RESULT contract

`RESULT` currently depends on:

> “the format the dispatch set”

If the dispatch does not define a format, different executions can produce inconsistent results.

**Fix:** define a default RESULT structure for cases where the dispatch provides none.

Suggested:

```text
RESULT:
- changed: <files/items>
- commands: <commands + exit codes, when applicable>
- verification: <tests/checks, when applicable>
- operation: <commit/branch/tag/service state, when applicable>
```

---

#### P1 — Assumptions can silently become decisions

The contract permits assumptions in `NOTES`, but some assumptions can change the work.

**Fix:**

```text
Any assumption that changes target, scope, command, acceptance, or safety
is a block. Only non-material assumptions may be recorded in NOTES.
```

---

#### P1 — Extra verification is not explicitly forbidden

The GATE law says to run the named command, but the executor could interpret “verify” as permission to run additional tests.

**Fix:**

```text
Run only gates named by the dispatch. Never add, alter, weaken, or
substitute a gate.
```

---

#### P1 — Misfit vs ambiguity needs a sharper boundary

TRANSFORM says a misfit should be listed and left, while the Andon Cord says ambiguity should block.

These are compatible, but the distinction should be explicit.

**Fix:**

```text
A misfit is an item that unambiguously belongs to the requested set but
cannot satisfy the transformation rule. Uncertainty about whether an item
belongs to the set is a block.
```

---

#### P2 — Recovery capture should account for unavailable artifacts

PID, stack, handles, and logs are required, but not every target exposes every artifact.

**Fix:**

```text
Capture every applicable volatility artifact available: PID, stack,
handles, and relevant log tail.
```

---

#### P2 — Secret-redaction scope is too narrow

The contract mentions credentials and tokens, but command output may contain other secrets.

**Fix:**

```text
Redact credentials, tokens, API keys, cookies, private keys, passwords,
and other secrets as `[redacted: <name>]`.
```

---

## 2. `executor-fast-read`

### What is working well

- Very strong capability boundary: `Read`, `Glob`, and `Grep` only.
- Clean separation between RECON, EXTRACT, and VERIFY.
- TOTALITY is appropriate for repository searches.
- DIPLOMATIC TRANSCRIPTION protects against accidental paraphrasing.
- NULL HYPOTHESIS prevents unsupported conclusions.
- No-shell/no-web constraint makes routing straightforward.
- Compact output contract is appropriate for a read-only executor.

### Findings

#### P0 — VERIFY is overly restrictive

The current rule says:

> “only a cited line moves it”

This is too narrow for repository verification.

For example, an exhaustive search can establish that no matching item exists **within the defined search scope**. Likewise, directly comparing two files can establish a mismatch without requiring a single “cited line.”

**Fix:**

```text
THE NULL HYPOTHESIS — A claim starts NOT ESTABLISHED. Positive or
contradictory evidence must be cited. An exhaustive search over the
dispatch's defined scope may establish absence within that scope.
Incomplete or ambiguous searches are NO EVIDENCE, never a negative claim.

RESULT: CONFIRMED | CONTRADICTED | NO EVIDENCE.
```

---

#### P1 — “No test proves the result” doesn't fit read-only work

RECON and EXTRACT don't necessarily have a test.

**Fix:**

Replace:

```text
no test proves the result
```

with:

```text
no available evidence can establish the requested result
```

---

#### P1 — “Failed command” is inherited from the write executor

This agent has no shell, so “failed command” is irrelevant.

**Fix:**

```text
Every skipped read, failed read, unfound item, misfit left, or output cut
is written down.
```

---

#### P1 — Byte-level transcription exceeds the tool capability

The contract says:

> “Reproduce bytes as-is”

but `Read` is fundamentally a readable-text operation.

**Fix:**

```text
DIPLOMATIC TRANSCRIPTION — Reproduce readable source text exactly as
returned by the read operation; do not normalize, paraphrase, or silently
repair it.
```

---

#### P1 — Assumptions should not be allowed to change interpretation

Same issue as `executor-fast`.

**Fix:**

```text
Any assumption that changes target, scope, interpretation, or acceptance
is a block. Non-material assumptions may be recorded in NOTES.
```

---

## Root cause

The underlying issue in both contracts is the same:

**The contracts are strong on operational discipline but slightly less explicit about the boundary between evidence, assumption, ambiguity, and absence.**

That creates two possible failure modes:

1. **Over-blocking** — the executor refuses a task that its available tools can actually establish.
2. **Silent interpretation** — the executor makes a seemingly harmless assumption that actually changes the requested work.

The fix is not to make the agents smarter.

The fix is to make the **decision boundary more explicit**.

---

## Recommended shared principle

Both agents should follow this hierarchy:

```text
Explicit dispatch
      ↓
Available capability
      ↓
Defined target / scope
      ↓
Observable evidence
      ↓
Requested result
```

If any step is ambiguous in a way that changes the work:

```text
BLOCKED
```

If the requested result can be established from available evidence:

```text
EXECUTE / READ
```

If an item is clearly in scope but cannot satisfy the rule:

```text
MISFIT → leave it → report it
```

If the evidence is insufficient:

```text
NO EVIDENCE
```

Never fill an evidence gap with a guess.

---

## Final assessment

### `executor-fast`

**8.5/10 → ~9.5/10 after fixes**

Strong mechanical executor. The biggest missing piece is a default RESULT contract and a sharper assumption/ambiguity boundary.

### `executor-fast-read`

**9/10 → ~9.5/10 after fixes**

Already very clean. The biggest correction is the VERIFY rule: exhaustive, explicitly scoped read/search operations should count as evidence for absence within that scope.

### Overall

The two agents form a good execution pair:

```text
                 ┌──────────────────┐
                 │   Fully specified │
                 │      task         │
                 └────────┬─────────┘
                          │
             ┌────────────┴────────────┐
             │                         │
          READ ONLY?                 CHANGES/
             │                       RUNS?
             ▼                         ▼
   executor-fast-read           executor-fast
             │                         │
     RECON / EXTRACT /          EDIT / IMPLEMENT /
         VERIFY                 OPERATE / RECOVER /
                                    TRANSFORM /
                                    GATE / REPRODUCE
             │                         │
             └────────────┬────────────┘
                          │
                   Ambiguous /
                 judgment-bearing
                          │
                          ▼
                 executor-smart
```

The important design principle to preserve is:

**Fast agents should not make decisions to compensate for missing specification. They should either execute the frozen instruction, report observable evidence, or block.**
